# AGENTS.md — Камертон

Закон проекта. Исполнитель читает его до первой строки кода.
Концепция: `docs/concept-v2.md`. Наряды волны 1: `docs/volna-1-issues.md`.

---

## 1. ЯЗЫК РЕАЛИЗАЦИИ

Приложение пишется **только на Metalogos (.mlog)**. Rust, Python и любой другой
язык в коде приложения запрещены.

Исключения, и только они:

- Mini App — HTML и JavaScript в браузере (PPG через камеру, пейсер, графики).
- Хостовые скрипты вне приложения: автостарт, бэкап базы.

Чего не хватает в языке — дописывается в Metalogos отдельным нарядом, по
протоколу затыка ниже. Обход на другом языке — дефект категории A.

## 2. ПРОТОКОЛ ЗАТЫКА

Исполнитель, упёршийся в отсутствующую возможность языка, **останавливается и
заявляет громко**. Молча обойти — худшее, что можно сделать.

Заявление содержит ровно четыре пункта:

1. Какой наряд упёрся и на каком шаге.
2. Чего именно нет — имя билтина, конструкции или поведения.
3. Минимальная программа `.mlog`, воспроизводящая отказ, и точный текст отказа.
4. Предложенный выход: наряд в язык, правка концепции через ADR или отказ от
   функции.

**Запрещено** до решения владельца: обходить на другом языке, ставить
заглушку, менять критерий приёмки, «временно» хардкодить значение, тихо
сужать задачу.

Решение принимает владелец. Тихий обход — дефект категории A, PR
откатывается без обсуждения. Громко заявленный затык дефектом не является:
это нормальный результат работы.

## 3. ЗАВИСИМОСТЬ ОТ ВОЛН ЯЗЫКА

Волна 1 Камертона не стартует, пока не принята волна 30 Metalogos
(`docs/metalogos-volna-30.md`). Блокирующие наряды языка названы в каждом
наряде приложения в разделе «Связь».

Волна языка открывается **только когда фаза приложения упёрлась в конкретную
стену**. Возможности «на будущее» в язык не заказываются.

## 4. ДОСТУП И СЕКРЕТЫ

- Агенту-исполнителю выдаётся PAT с минимальными правами и сроком жизни на
  одну волну. После пост-приёмки токен отзывается.
- Токен живёт только в окружении машины исполнителя. В коде, в репозитории,
  в issue, в PR и в переписке — никогда.
- Чтение секретов в теле маршрута закрыто по умолчанию; имена открываются
  через `METALOGOS_ENV_ALLOWLIST`, список фиксируется в `deploy/`.
- Утёкший секрет отзывается немедленно, до продолжения любой работы.

## 5. ИНВАРИАНТЫ ПРОЕКТА

Нарушение любого из семи — дефект, а не компромисс. Меняются только через ADR.

1. **Измерительное ядро неизменно.** Метрики отклика, формула награды, клапан
   честности и схема пробы закрыты для `adapt`. Самомодификация касается
   только формулировок и текстов.
2. **Контекст слеп до записи отклика.** Фаза Луны, погода, выбранный звуковой
   режим не показываются, пока отклик не залогирован.
3. **Награда оптимизирует движение.** Компоненты: отклик в моменте 0,2 ·
   сдвиг через сутки 0,3 · действие в сторону ноты за 72 часа 0,5. Каждый
   компонент пишется с флагом присутствия, награда — взвешенная сумма
   присутствующих, нормированная на сумму их весов. «Отклик в моменте»
   имеет два источника с объявленным приоритетом: проекция на доминантную
   частоту с M2, субъективные шкалы до неё; использованный источник
   фиксируется в пробе и клапаном честности не смешивается молча
   (ADR-0001).
4. **Клапан честности обязателен.** Система сравнивает себя со случайным
   выбором и прямо пишет «сигнала нет», когда не выигрывает.
5. **Разведка не отключается.** Минимум 20% проб — принудительный перебор.
6. **Данные переживают код.** SQLite, читаемый сторонним клиентом без
   приложения. Приложение воспроизводится, датасет — нет. Бэкап еженедельно.
7. **Данные не покидают машину владельца.** Голос, отклики, нота, пульс
   обрабатываются локально. Наружу — только публичные запросы к научным базам.

# ============================================================
# QUALITY OS v1.0 — установка эталонной дисциплины проекта
# ============================================================

КОНТРАКТ
Слово «готово» имеет силу только после независимой проверки.
Качество строится процессом, а не обещанием исполнителя.

ДИСЦИПЛИНА — конвейер каждой задачи (пропуск шага запрещён)
1. РЕКОГНОСЦИРОВКА — снять факты (код, issues, доки) до выводов.
2. НАРЯД — Шаг 0, границы файлов, критерий приёмки.
3. ИСПОЛНЕНИЕ — только в границах наряда; заглушки запрещены.
4. ВЕРИФИКАЦИЯ — второй независимый метод; проверяет не исполнитель.
5. WORKLOG — append-only журнал: что сделано и чем проверено.
6. ДОКИ — techdocs и README обновляются в той же волне работ.

АУДИТ
- Любое утверждение воспроизводимо: источник, метод, след в worklog.
- Сделанное перепроверяется чужими глазами по чек-листу, не по памяти.

ЖЕЛЕЗНЫЕ ЗАПРЕТЫ
- Заглушки, TODO-имитации, «почти работает».
- Точечные оценки — только диапазон low / expected / high.
- Секреты в коде; сетевые вызовы без таймаутов и ретраев.
- Цифры без проверки: каждая проходит размерность + второй метод.

ТЕСТИНГ
- Пирамида: юнит → интеграция → e2e на критических путях.
- Мутационная проверка: тест обязан поймать внесённый дефект.
- Каждый баг закрывается правкой плюс тестом, который его ловит.

ДОКУМЕНТИРОВАНИЕ
- Правка кода и правка доков идут одним коммитом, не «потом».
- Решения фиксируются как ADR: контекст → альтернативы → цена.
- Язык доков единый (English-only), без расхождений с кодом.

СИСТЕМНАЯ ПРОВЕРКА (приёмка)
- Верификатор не исполнитель; провал → reopen + revert.
- Операции идемпотентны: повторный запуск ничего не ломает.
- Волна закрывается только при ALL GREEN, иначе возврат на доработку.

ИТОГ: «эталон» подтверждается протоколом проверки, а не словами.

# ============================================================
# NARYAD CONVEYOR v2 — система работы с нарядами
# ============================================================

ФОРМАТ НАРЯДА Ш1 (один наряд = один issue = один PR)
- Шаг 0 — что проверить ДО начала работы (снять актуальный статус)
- Факт — реальность по рекогносцировке, а не догадки
- Задача — что именно делается
- Сделано когда — проверяемый критерий приёмки
- Границы — файлы/модули, трогать которые разрешено
- Связь — ссылки на план, соседние наряды, прошлые волны

КОНВЕЙЕР (строго по порядку, пропуск шага запрещён)
 1. ПЛАН — взять партию работ из стратегического плана;
    в одной волне наряды не имеют коллизий same-file.
 2. НАРЯД — составить по форме Ш1, без размытых формулировок.
 3. ISSUE — опубликовать идемпотентно (HTML-маркер как SSOT).
 4. ДИСПАТЧ — запустить волну исполнителем (Actions/агент).
 5. КОДИНГ — только в границах наряда; заглушки запрещены.
 6. ПРОВЕРКА — тесты + независимая верификация вторым методом.
 7. КОММИТ — атомарно: одно логическое изменение = один коммит.
 8. ПУШ → PR — в теле PR обязательно «Closes: #N» (issue наряда);
    посторонние issue упоминаются только через «Refs:».
 9. МЕРЖ — squash конвейером; issue закрывается сам через Closes —
    закрывать руками запрещено.
10. ПОСТ-ПРИЁМКА — верификатор (не исполнитель) гоняет волну после
    мержа: ALL GREEN → принять; провал → reopen issue + revert PR.
11. ОТЧЁТ — worklog (append-only): что сделано и чем проверено;
    нет следа в worklog = не сделано. Далее сводка владельцу.
12. ДОКИ — techdocs и README обновляются в той же волне, не «потом».

ЖЕЛЕЗНЫЕ ПРАВИЛА
- Волна считается закрытой только при ALL GREEN по всем нарядам.
- Верификация всегда пост-приёмочная: сначала merge, потом строгая
  проверка, провал откатывается reopen + revert без торга.
- Повтор любой операции безопасен: идемпотентность обязательна.
- Попутные правки вне границ наряда запрещены даже «мелкие».

ИТОГ: наряд живёт по кругу план → issue → диспатч → PR → приёмка
→ отчёт → доки, и каждый шаг оставляет проверяемый след.
